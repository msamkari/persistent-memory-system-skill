# Persistent Memory System — Claude Skill

A persistent, external memory system for any long-running project — freelance work, a small business, a negotiation, research, or ongoing family tracking. This Skill has Claude build and run a durable reference stored in a real file service (Dropbox, Google Drive, Microsoft 365, or Notion with adaptation), with a mandatory full read at the start of every session and complete archiving — never deletion.

*Open the folder and read exactly what Claude will read next session, no black box.*

This repository hosts the source, packaged releases, and test evidence for the Persistent Memory System Skill, developed and maintained by Mohammad Samkari.

## Version history

**v1** (2026-09-16): First build, tested across 5 scenarios via skill-creator (parallel subagents, with_skill vs. without_skill). Result: 100% vs. 50.3%, in the 5 scenarios we tested (10 agent runs). Caveat: the without_skill baseline runs still inherited the project's existing context (prior conversation history and files) rather than starting from a blank slate, so part of the gap may reflect that inherited context rather than the Skill alone. Actually installed on Mohammad's account.

**v2** (2026-09-18): A comprehensive improvement round with five tasks: (1) An attempt to improve the trigger description via the automated skill-creator tool — a real environment constraint was discovered (the tool registers the file as a slash command rather than a true skill in this version of Claude Code, producing 0% recall regardless of the description); this was documented clearly, and a workaround (direct subagent judgment) was used to manually craft an improved description. (2) Expanded testing to 19 scenarios (9 training + 6 hidden test + 4 special cases), 100% success verified directly against the files. (3) Testing of Notion, Microsoft 365, and a real messy-folder audit — detailed in the report. (4) The first real test of a centralized multi-project Dashboard. (5) A quality review against official skill-creator standards (no restructuring needed at this time).

**v3** (2026-09-18): A deep adversarial test round with three tasks, explicitly aimed at finding the mechanism's limits rather than confirming its success (278 → 362 lines). (1) Local storage support (Claude Code/Desktop/Cowork with a connected device) as a third option alongside cloud storage — full success, plus a fix for a real gap (a CLAUDE.md substitute for the Project-instructions mechanism unavailable locally). (2) Real concurrency race tests (genuinely parallel subagents, not sequential simulation): a four-way race succeeded 100% with no intervention, but additional tests targeting the check-before-write gap uncovered three real bugs in the original archiving rule — an archive-name collision that could silently erase a historical version, a timing gap between the freshness check and the actual move that could archive the wrong file, and the absence of any instruction for the "file disappeared entirely" case (as opposed to just "file changed") — all three were fixed with new explicit instructions and re-tested with fresh real races, confirmed successful; one architectural limit was documented honestly as a real constraint that cannot be fully eliminated by text instruction alone (the check-then-act gap between two separate tool calls). (3) A deep check of sensitive-data handling (.env, JWT, card numbers) — zero leakage confirmed by direct independent verification, plus a new proactive explicit instruction preventing any sensitive value from being copied literally into any system file.

**v4** (2026-09-19): One design clarification, no new test round (362 → 380 lines). During the Skill's first real production use (a separate memory system for two sub-projects), a small unintended design contradiction was discovered: the "current file status" line in the header of an append-only narrative file becomes stale the moment a real entry is added, but the "never edit an old entry" rule for that same file created ambiguity over whether this line is a closed historical entry or a live summary. An explicit clarification was added to the "File categories and numbering" section: this line is an updatable live summary, not a historical entry — updating it does not violate the rule, under two conditions together: (1) it is done exclusively through the normal archiving mechanism (moving the full current version to the archive first, then writing a new version), and (2) it is never updated automatically without permission — the new wording is shown to the project owner and their explicit approval obtained first. Zero bug fixes this round.

**v5** (2026-09-19): A complete rewrite of the optional Handover step's description in the "Natural Path" section (380 → 401 lines), using ready English text supplied verbatim by Mohammad. The old description was two brief lines; the new text specifies five fixed parts, in order, for any Handover from prior conversations: (1) situation and history, with an outcome note for each prior attempt, (2) the current plan, broken into clear phases if any exist, (3) people involved and their roles, (4) key dates and any changes to them with current status, and (5) outstanding items, with longer-term context if relevant. It emphasizes pulling only what's actually there without inventing anything, writing the output in the same plain narrative-file format (not a separate document), and ending the draft with one specific question rather than a general one. Fully independent of any other skill — zero reference to any structured-handover-doc structure (verified by grep). Zero bug fixes this round.

**v6** (2026-09-20): A fix for a real activation false negative, plus fixes for two Handover gaps, plus two new additions (401 → 473 lines), following a real production report and an explicit request from Mohammad. (1) The Skill's description was redesigned to trigger on any vague, general "system" request for a project regardless of its history, unless the request explicitly names a different kind of system — plus a new clarifying-question rule for ambiguous cases. (2) Handover step: an explicit check for the availability of the conversation-search tool was added before any promise of a result, and a new section permanently prevents information from one sub-project leaking into a sibling sub-project sharing the same folder (the multi-project-in-one-folder pattern). (3) A new rule: stop immediately and state precisely if the storage tool suddenly stops working mid-operation (read/write/archive) during the same session that it had been working in, rather than assuming the last known content is still current or fabricating a substitute. **Two remaining risks, documented explicitly, not hidden:** (a) The description's activation on severe-ambiguity cases was confirmed by a 3-of-4 majority of independent judges on the original production case, not full consensus — one dissenting judge still sees a possibility that the project's visible topic could override the ambiguity rule in rare cases. (b) The sub-project isolation rule was tested successfully only against clearly-labeled dummy data; real, unlabeled data of the same kind was not tested directly, and the "when in doubt, exclude" rule is the safety net designed for that possibility, not tested evidence in its own right.

**v7** (2026-09-22): Two new additions, following an explicit request from Mohammad (220 → 238 lines). (1) **Centralized Projects Index**: a root-level `_Projects_Index.md` file, its read pattern, and a mandatory mechanical exclusion rule ("when in doubt, exclude") for any project structure that is shared across multiple people or otherwise sensitive by nature — the rule is written in general, reusable terms, with a shared-sibling-projects structure and a family estate/legal-proceedings project given as concrete, explicitly named illustrative examples directly in the Skill's own text, not only in a separate index file. (2) **Expanded centralized Dashboard**: a new "reading at scale" guideline (batch reads of 5–8 files at a time rather than one large parallel burst, with retry-then-report-failure on throttling) and a new "anomalous project states" section with explicit handling rules for four cases — a missing or empty project summary, a malformed or unreadable summary, duplicate project entries, and a stale project. Both additions were tested directly: the Index's exclusion rule against real adversarial-pressure scenarios naming the two real illustrative cases (4/4 pass), and the Dashboard's batching and anomaly rules against a real 40-fake-project Dropbox sandbox covering all four anomaly types at least twice each, run through an independent agent (all four types correctly identified and handled). **One honestly documented residual gap:** the "retry on actual throttling" branch of the new batching rule was not directly exercised within that test run itself, because the test agent's own disciplined batching never triggered a rate limit — it is corroborated only indirectly, by an unrelated rate-limit event encountered during the test sandbox's own setup.

**v7.1** (2026-09-28): One addition, following an explicit request from Mohammad, made after a full privacy scan of this repository (root files, every packaged release v2 through v7, and every archived `testing-evidence` zip) found zero mentions of any real project or child name — the Skill's own text already used only generic illustrative examples. The addition: an explicit **provenance rule** in the "File categories and numbering" section — when writing a narrative-log entry, every significant claim must be marked as one of three things: something the user explicitly stated or decided, something verified directly (a real test run, a file actually inspected, a tool result), or Claude's own inference or recommendation — the third must never be recorded as if it were the first or second, using a plain in-sentence marker ("inferred, not confirmed:", "recommended, not yet decided:") rather than per-line tags, consistent with the existing plain-text formatting rules. Tested directly: an independent agent given a short scenario mixing all three kinds of claims wrote a log entry that correctly distinguished them in plain text, with no per-line tags and no inference recorded as fact.

**v8** (2026-09-28): One addition, following an explicit request from Mohammad (240 → 244 lines). The addition: a new **Long-running jobs** rule — when given a job with three or more phases, or any job likely to outlast the context window or a usage limit, save the user's specification verbatim (every quoted sentence, number, and piece of exact wording untouched) to a dedicated job file in the project's own `Jobs/` folder before starting phase 1, with a STATUS block for phases done/pending; re-read that file at the start of every phase and after any interruption or context compaction, instead of relying on conversation memory or a summary; append one dated status line per phase; and treat any content added to the file that the user didn't write as untrusted, confirming with the user before acting on it. Placed next to the archiving/provenance rules, with the frontmatter description unchanged (verified with a full diff). Tested directly with five independent real-agent runs in an isolated fake-data sandbox: save-before-start, recovery from only a two-line summary after simulated compaction, correctly stopping and reporting instead of improvising when the job file was missing, correctly leaving an untrusted line alone and asking before acting on it, and a regression check confirming the frontmatter description and the rest of `SKILL.md` were otherwise unchanged — all five passed on the first run, with no wording fixes needed. **Honestly documented limits:** the rule does not specify a resolution mechanism for two sessions writing to the same job file at the same time (the same category of gap the v3 archiving-rule fixes address for `System_Current_MD` files, not extended here to `Jobs/`); and it gives no explicit procedure for correcting an already-appended status line later found to be wrong, beyond the general narrative-log convention used elsewhere in this Skill (a dated correction note rather than editing the original line).

**v8.1** (2026-09-29): One small addition, following an explicit request from Mohammad, made right after a real gap surfaced during v8's own closing phase (244 → 248 lines). During that closing phase, a piece of Arabic wording that had been shown to Mohammad for approval (a translated paragraph for `00_Archiving_Rule.md`) was lost across a context compaction — the v8 job file recorded only the fact that a proposal had been made, not its literal text, so the exact wording could not be reconstructed from conversation memory afterward. The gap was closed at the time by going back to the one confirmed real source available (the live `SKILL.md` on this repository's `main` branch) rather than comparing two memory-reconstructed candidates. The addition: a new **Proposals awaiting approval** rule, placed directly after Long-running jobs — when a phase produces wording, a draft, or a decision proposal that needs the user's explicit approval before being written to a permanent file, that exact text is saved to the job file's status log the moment it is proposed, not just noted as proposed; a pending approval is treated as part of the job's recoverable state, the same as the original spec. Verified with a full diff against the prior `SKILL.md` that this four-line addition is the only change, and the YAML frontmatter is unchanged. Tested directly with a two-part independent-agent run in an isolated sandbox: one agent proposed an exact draft paragraph mid-job and saved it verbatim to the job file's status log at the moment of proposing it (confirmed independently by re-fetching the file, not by trusting the agent's own report); a second, separate agent given only a short post-interruption summary and the job file's path, with no proposal text at all, correctly re-read the job file and recovered the exact pending text, the correct blocking phase, and the correct next step. **Honestly documented note:** the first attempt at this test was itself invalid — an agent was given the candidate file's content embedded in its instructions using shell-style syntax that the dispatching tool does not evaluate, so it ended up operating on an older version of `SKILL.md` without anyone noticing until its own report flagged the mismatch; the test was discarded and re-run correctly by having each agent fetch the real candidate file directly.
